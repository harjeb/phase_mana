# 本机主持等待房间

构筑联机现在将等待房间与实际引擎对局分开：

1. 主持人创建空房间并获得邀请，不需要预先填牌表。
2. 其他人粘贴邀请进入同一房间，双方起初都未入座。
3. 点击空座位入座；房主可以选择任意位置，不固定占座位 1。
4. 房主设置赛制与人数；每个人从自己的套牌或对应赛制的预设中选择套牌并提交。
5. 所有人就绪后，房主开始对局。更换套牌、改变赛制/人数或断线会取消相关准备状态。

当前房内赛制选择支持标准、摩登、先驱、薪传、特选、纯普、指挥官和双头巨人；双头巨人固定四座。轮抽仍使用联机页原有的独立轮抽入口。这个等待房间不会把选择「限制赛」误当作已经进行了轮抽。

## 房间与引擎的边界

`server/src/waiting_room.rs` 管理成员、座位、赛制、私有套牌、准备状态及启动屏障。公开广播只包含成员名字、座位、连接状态、套牌名字和准备状态，不含牌表或成员凭据。

主持服务的公开端口同时提供 `/room` 等待房间 WebSocket 和 `/ws` 原生引擎连接转发。原生 Phase 引擎监听单独的回环端口；主持人的本机控制 API 仍使用原来的回环 Host/Origin 校验。创建房间需要本机控制 API 返回的随机能力凭据；邀请只携带房间加入密码，不携带主持控制凭据或任何人的重连令牌。

实际启动时，以座位 1 的成员创建原生游戏（不一定是房主），并按座位顺序逐个加入其余成员。每个人的 `SessionAttached` 都得到确认之后，才发送手动开始命令。原生 `start_when_full` 关闭，因此入座和提交套牌不会自动开始。引擎仍负责套牌与游戏规则验证。

启动失败或启动期间断线会让同一个房间返回等待状态，保留套牌、取消准备并清理客户端的未完成对局连接。成员凭据保存在各自标签页的 `sessionStorage`，可以重连原座位。主持人「关闭房间」会停止本机引擎。

## 运行和验证

需要重新编译并重启本机 API 服务，旧进程没有新的 `/room` 监听器。前端遇到旧服务会明确提示更新，不会提交空套牌来冒充等待房间。

- `cargo build --manifest-path server/Cargo.toml --bin phase-mana-server`
- `npm run host:build`：构建协议 76 / ManaBrew 2 的固定版本原生引擎及完整卡牌数据。
- `npm run e2e:host`：需要前端开发服务正在运行。测试启动自己独立的本机 API 和原生引擎，使用两个独立浏览器验证空房间、邀请、反向座位顺序、选牌、准备重置、私有信息和实际对局启动；不会关闭开发者现有房间。

环境变量 `PHASE_HOST_LAN=1` 才会开放局域网监听；`PHASE_HOST_PUBLIC_URL` 应指向等待房间服务的公开端口，转发需同时支持 `/room` 和 `/ws`。仅回环的默认邀请仍只在本机可用，创建房间不会自动建立公网隧道。

Windows 接受的 TCP 流会继承非阻塞监听器的状态，因此转发前明确恢复为阻塞流；单元测试覆盖等待一段时间后仍能双向传递原生 WebSocket 帧。
